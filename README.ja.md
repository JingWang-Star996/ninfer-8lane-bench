# 単一の RTX 5090 Laptop で 1508 tok/s — Qwen3.8-27B NVFP4、8 レーン同時実行

[English](README.md) | [简体中文](README.zh-CN.md) | **日本語**

> RTX 5090 **Laptop**（24 GB）1 枚で 27B モデルを動かし、8 レーン同時で合計 **1508 tok/s**。
> ここで扱うのは**バースト時のピーク**だけです。日常的なスループットは別に記載していますので、両者を混同しないでください。

## TL;DR

| シナリオ | レーン | MTP draft | token/ラウンド | アクセプト率 | 単一ストリーム | 8 レーン end-to-end | 8 レーン engine peak |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **バーストピーク** | 8 | **15** | 15.98 | 99.9% | 325.4 | **1302.9** | **1508.0** |
| バーストピーク | 8 | 8 | 9.00 | 100% | 233.6 | 858.5 | 891.4 |
| 日常（マルチエージェント） | 8 | 6 | 5.90 | 81.8% | — | 465–490 | 784.5 |

単位は tok/s。ハードウェアもモデルも同一で、3 行の違いは**すべて MTP のドラフト深さ**によるものです。

1508 という数字を 1 行で書くとこうなります。

```
1508 tok/s ≈ 8 レーン × 16 token/ラウンド × 11.8 ラウンド/秒
```

3 つの因子はそれぞれ、レーン数（エンジン側の上限）、1 ラウンドで確定できる token 数（ドラフト深さ × アクセプト率）、ラウンド速度（電力制限とカーネル効率）に対応します。

> ⚠️ **「ドラフトを深くすればもっと速くなる」は誤りです。** 実測では draft を 15 から 16 に上げると
> ピークは 1473 から 924 に落ち、23 まで上げても 1027 でした。verify 幅 16 は安全マージンではなく、
> ファストパスの境界です。詳細は [results/width-sweep.md](results/width-sweep.md) を参照してください。

## 3 つの計測定義

疑問のほとんどは定義の混用から来ます。どの数字がどこから出たのかを、ここで固定します。

### 1. engine peak（`decode=`）

エンジンは 5 秒ごとに 1 行出力します。`decode` はそのウィンドウ内で確定した decode token 数 ÷ ウィンドウ長です。

```
[2026-11-05 14:22:43.298] throughput interval=5.008s prefill=0.0tok/s decode=1508.0tok/s
                          running=8 prefilling=0 decode_ready=8 waiting=0 avg_decode_batch=8.00
```

この 1 行は 3 つの条件を同時に満たしており、よくある指摘をその場で排除できます。

- `prefill=0.0` → prefill の水増しがなく、**純粋な decode**
- `avg_decode_batch=8.00` + `waiting=0` → 8 レーンが実際に飽和、待ち行列なし
- `running=8 / decode_ready=8` → 遊んでいるレーンがない

### 2. end-to-end 集計

スクリプトは**最後まで完走した**全リクエストの `usage.completion_tokens` を合計し、全アクティブリクエストの
実時間（最初の token から最後の token まで）で割ります。

エンジン値より 13% ほど低く、差分は TTFT とリクエスト切り替えの隙間です。
**この数字のほうが工作しにくく、対外的にはこちらを引用しています。**

### 3. 単一ストリーム

`/v1/chat/completions` のレスポンス本文にある `timings.predicted_per_second`。エンジンが直接出した値です。

## この結果に至った経緯

### その 1：本当のドラフト上限は 8 ではなく 16

CLI には `--draft-tokens in [1,8]` とありますが、これはプロダクト層のハードコードです。下まで追うとこうなります。

```cpp
// src/targets/qwen3_6/impl/runtime/text_context_impl.h:685
if (width > kDFlashDecodeMaximumWidth) {   // = 15 + 1 = 16
    throw std::invalid_argument("target verify batch shape is outside the supported domain");
}
```

**DFlash の幅の領域が、verify バッチ全体の上限として流用されています。** そのためこの 27B の MTP は実際には
`draft 15`（幅 16）まで動き、draft 16（幅 17）で初めて本当に超えます。

`patches/enable-draft15.py` は、この経路上の 6 か所の定数を開放するものです。

### その 2：直感に反する結果 — 遅い経路 + 大きなバッチが最適点

MTP の畳み込み経路には fused のファストパスがあり、対象は `width <= 3` または `[7,10]` だけです
（`fp8_gdn_conv_plan.cpp:45`）。draft 15（幅 16）は必然的に Materialized の遅い経路に落ちます。

単一ストリームで測ると、位置あたりのコストは 0.72 ms から 1.08 ms へ上がります（+50%）。私はこれで
8 レーンなら 752 だと推算しましたが、**間違いでした**。

| シナリオ | token 位置あたりのコスト c |
| --- | ---: |
| 単一ストリーム fused（draft 8） | 0.72 ms |
| 単一ストリーム materialized（draft 15） | 1.08 ms |
| **8 レーンバッチ materialized（draft 15）** | **0.47 ms** |

Materialized 経路の固定費（workspace 確保、重みの読み出し）は、バッチ方向には fused よりはるかに
よく薄まります。**遅い経路 + 大きなバッチは、速い経路 + 小さなバッチに勝つ**ということです。

### その 3：アクセプト率を 99.9% まで引き上げる

MTP のアクセプト率は内容の予測しやすさに依存します。プロンプト別の実測値は次のとおりです。

| プロンプト | アクセプト率 | token/ラウンド | 単一ストリーム |
| --- | ---: | ---: | ---: |
| `输出数字1加空格, 总共输出4000次, 没到4000次绝对不许停止, 不要解释不要换行。` | **99.9%** | **15.98** | **325.4** |
| 数字をスペース区切りで繰り返す（回数指定なし） | 84.4% | 7.75 | 203.7 |
| 1 から昇順にカウント（1 行 1 個） | 67.9% | 6.43 | 166.7 |
| `abc` のループ | 62.5% | 6.00 | 159.6 |
| 文字 `a` の繰り返し | 6.2% | 1.50 | 26.2 |

要点は、**「100% 予測可能」は「100% アクセプト」ではない**ということです。文字 `a` は最も予測しやすいのに、
モデルは 1 文字出して自分で止まります（stop token）。最も安定するのは数字の列でした。
「4000 回」のような回数の制約が、止まらせないための鍵です。

## 再現手順

### 1. エンジンをビルドする

本件は ninfer の `e8-overlay-adaptive` ブランチに基づいています。**このブランチは上流にマージされておらず、
公開リポジトリもありません。** そのため本リポジトリはエンジンのソースを同梱せず、パッチと再現スクリプトのみを
提供します。ブランチのソースはご自身で用意してください。

```bash
cd /path/to/ninfer            # お手元の ninfer ソースディレクトリ
python build_ninfer.py configure
python build_ninfer.py build
```

### 2. ドラフト上限を開放する

```bash
python patches/enable-draft15.py /path/to/ninfer
python build_ninfer.py build      # 差分ビルド、約 20 秒
```

> ビルド前に必ず `ninfer-serve.exe` を停止してください。起動したままだとリンクが失敗します（LNK1104）。

### 3. 8 レーンのプロファイルで起動する

```bash
NINFER_DRAFT=15 NINFER_CUDA_GRAPH=1 python build_ninfer.py serve8
```

### 4. ベンチマーク

```bash
python scripts/bench_quick.py 20 8 predict
```

同時にエンジン側も監視します。

```bash
grep "throughput interval" serve.log | grep "running=8"
```

## 自作ベンチスクリプトの 2 つの罠

自分でスクリプトを書くと必ずと言っていいほど踏みます。結果は大きくずれます。

### 罠 1：response checkpoint の再利用でリクエストが即死する

同じプロンプトを連投すると、エンジンは同一プレフィックスと判断し、
`reuse=restore_response_checkpoint` の後すぐに stop token を踏んで 2 token しか出しません。

```
[req 614] done finish=stop_token gen=2 cache=40 reuse=restore_response_checkpoint
```

**対策**：リクエストごとに一意なサフィックスを付ける（スクリプト側で実装済み）。

### 罠 2：モデルが自分から止まる

数字の昇順カウントは 292 個で止まり、CJK の短い文は 1 回で止まります。assistant prefill を使っても
効果がありません（`gen=2`）。

**対策**：プロンプトに回数の制約を明記する。

この 2 つを踏むと、計測値は 5 分の 1 まで落ちます。

## さらに速くできるか：2 つの失敗した試み

1508 のあと、2 つの道を試して両方とも壁に当たりました。同じ回り道をしないよう、ここに残します。

### 試み 1：12 レーンへの拡張（失敗）

8 レーンはエンジンのハード上限です。12 レーンには GDN replay の行ジオメトリ変更が必要で、4 つの壁が
順に拒否します：`--max-concurrency must be in [1,8]` → `GDN replay record capacity exceeds eight rows`
（`kMaximumRecordCapacity = 8`）→ `kMaximumRows = 8` → カーネルは 8 行のフォールドジオメトリしか
登録していない。さらに重要なのは**計算が合わない**ことで、12 レーンの理論値は約 983 で 1000 に届きません。
そのためカーネル側を掘るのはやめました。

### 試み 2：ドラフト深さを 23 まで上げる（失敗、しかも直感に反するデータ）

draft 8 と draft 15 の 2 点から「ラウンド時間 = 75.5 ms + 0.59 ms × 位置数」をフィットし、これで外挿すると
draft 23 は 2143 tok/s になるはずでした。そこで 4 層の制限（CLI 上限、GQA workspace、RoundState ウィンドウ、
GDN 幅）を開放しました。ビルドは通り、draft 23 は正常に起動し、アクセプト率 98.7%、23.5 tok/ラウンド ——
**そして速度は半分になりました**。

| draft | verify 幅 | engine peak | end-to-end | token/ラウンド | ラウンド時間 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 15 | 16 | **1473.5** | 1199.1 | 15.98 | 87 ms |
| 16 | 17 | 897.1 | 760.5 | 16.78 | 145 ms |
| 19 | 20 | 988.8 | 866.8 | — | 147 ms |
| 23 | 24 | 1026.7 | 757.0 | 23.50 | 183 ms |

原因は `kSmallTChunkTokens = 6` です。幅 16 はちょうど 3 チャンク（6+6+4）で、最適化されたタイル形状です。
16 を超えると経路が変わり、1 ラウンドの固定費が 85 ms から 145 ms に跳ね上がります。遅い経路の
位置あたり限界コストは 5.4 ms で、ファストパスの 0.59 ms の 9 倍です。
**ドラフトを深くすれば確かに多くの token を確定できます（1.84 倍）が、1 ラウンドのコストが 2.1 倍に
なるため差し引きで負けです。**

隠れたコストもありました。幅 24 では workspace が大きくなるため、以前の `--kv-capacity 94208` は
確保に失敗し（97 MB 不足）、86016 まで下げる必要がありました。
**深いドラフトはコンテキスト長と引き換えで、しかも赤字です。**

### 2 つの失敗から言えること

1. **1500 前後がこのカーネル系の上限です。** ドラフトを深くしてもレーンを増やしても動きません。
2. **残された唯一のレバーは 1 ラウンドあたり約 75 ms の固定費**（重み 20 ms + verify 9 ms + スケジューリング／
   workspace 約 55 ms）であり、token/ラウンドではありません。同じモデルで固定費を半分にすれば幅 16 で
   2700 程度になりますが、**これも外挿であり未実測です。結論として引用しないでください。**
   方向性（固定費が支配的）は信頼できますが、数字は信頼できません。
3. **局所的な線形関係で外挿するのはやめること。** 0.59 ms は 1 つのファストパスの傾きであり、境界を越えると
   無効になります。これは後述の「過去に間違えた数字」と同じ種類の誤りです。

## 過去に間違えた数字

疑問の一部は私自身が作ったものです。ここで訂正します。

| かつて言ったこと | 実際の意味 | 本当の値 |
| --- | --- | ---: |
| 「8 レーンで 1200 / 1269 tok/s」 | 総 token ÷ **名目 12 秒**。実際のリクエストは 29〜103 秒動いていた | **489.6** |
| 「8 レーンで 780」 | エンジンの 5 秒ウィンドウのピークを、持続スループットとして提示 | 持続で約 **485** |
| 「ドラフトを深くすれば 2143」 | 2 点線形外挿。両アンカーともファストパス内で、境界を越えると傾きが 9 倍に変わる | **1026.7** |

1 つ目は純粋な計算ミスです。スクリプトが名目時間を分母にしており、3〜10 倍の水増しになっていました。
2 つ目は瞬間値と平均の混同で、780 は確かに存在しますが 5 秒サンプルであって 30 秒平均ではありません。

**現在の方針**：対外的な数字には必ず定義（`engine peak` / `end-to-end` / `単一ストリーム`）を添え、
ピークと持続を分けて報告します。

## 制約（重要）

1. **これはバースト時の話です。** 8 レーン × 16 token/ラウンドには、内容がほぼ完全に予測可能であること
   （アクセプト率 99.9%）が必要です。実際の会話、コード、エージェント作業ではそこまで行かず、
   1 レーンあたり 60〜70 tok/s、8 レーン合計で **465〜490 tok/s** です。
2. **draft 15 は普通の内容では draft 8 に劣ります。** アクセプト率が落ちると、深いドラフトの検証コストは
   純粋な無駄です。日常用途は 6 か 8 を使ってください。
3. **8 レーンはエンジンのハード上限です。** 12 レーンには GDN replay の行ジオメトリ変更
   （`kMaximumRows = 8`）と CUDA カーネル側の作業が必要で、本件では未実施です。
4. **上流に未マージのブランチに依存しています。** 上流が更新されれば、結論はすべて再検証が必要です。
5. **ラップトップのボトルネックは電力制限です。** 既定の 95 W では 8 レーンで約 580 tok/s にとどまり、
   179 W の結果とは 2.6 倍の差があります。これは冷却ではなく TGP の制約です。
6. **1500 はこのカーネルの上限であり、設定の問題ではありません。** verify 幅 16 を超えるとファストパスを
   外れ、ドラフトの深化もレーン増もマイナスです（上記 2 つの試みを参照）。さらに上を目指すには
   スケジューリングと CUDA Graph のカバレッジを変える必要があり、フラグでは届きません。

## 環境について

エンジンは自前ビルドの `ninfer-serve`（Windows ネイティブ、vLLM でも llama.cpp でもありません）。
選んだ理由は、すべてのパラメータがコマンドラインに露出しており、VRAM を MB 単位で計画できることです。
24 GB という厳しい制約では決定的でした。代償は、上流に未マージのブランチへの依存です。
